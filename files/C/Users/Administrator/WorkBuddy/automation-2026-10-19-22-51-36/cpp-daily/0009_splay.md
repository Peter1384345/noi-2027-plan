## 一、为什么高效

Splay 用一句话替代了红黑树的全部颜色规则：**访问谁，就把谁转到根**。

| 维度 | `std::set`（红黑树） | FHQ-Treap（0008） | Splay（本期） |
|---|---|---|---|
| 平衡依据 | 颜色不变式 + 插入修复 | 随机优先级 + 堆序 | **没有平衡条件**，只有提根动作 |
| 每节点额外字段 | 3 指针 + 颜色位 | l, r, pri, sz | l, r, **fa**, sz |
| 单次最坏 | O(log n) | O(n)（随机性失效时） | **O(n)**（均摊保证不约束单次） |
| 摊还/期望 | O(log n) | 期望 O(log n) | 摊还 O(log n) |
| 自适应（工作集局部性） | 无 | 无 | **有**：刚访问的键下次在根附近 |
| 区间翻转 / 按位置插删 | — | O(log n) | O(log n) |
| 可持久化 | — | 支持 | **不适配**（见第五节第 9 条） |
| 核心代码量 | 库内 ~800 行 | ~40 行（split + merge） | ~60 行（rot + splay） |

结论：纯查找负载下 Splay 的常数通常不如红黑树（每次操作都要付出旋转到根的代价），
它换来的是**两种别处拿不到的能力**：

1. **自适应**：访问分布有偏时（缓存、字典、编译器符号表），热点会自己浮到根附近，
   实际代价低于 log n；这是"无平衡条件"的直接红利，也是它唯一的"平衡"来源。
2. **区间即子树**：两次 `splay` 就能把任意区间夹成一个子树，于是区间翻转、区间加、
   按位置插删全部变成"对一棵子树打标记"。这就是竞赛里的**文艺平衡树**。

## 二、原理

### A. 唯一原语：`splay(x, goal)`

把 `x` 旋转到 `goal` 的孩子位置（`goal == 0` 表示转到根）。全部规则只有三种情形：

```
zig      y 就是目标            → 旋 x 一次
zig-zig  x 与 y 同向（左-左 或 右-右） → 先旋 y，再旋 x
zig-zag  x 与 y 异向           → 先旋 x，再旋 x
```

```cpp
while (t[x].fa != goal) {
    int y = t[x].fa, z = t[y].fa;
    if (z != goal) {
        if (DoubleRot && is_right(x) == is_right(y)) rot(y);   // zig-zig: 先父
        else rot(x);                                            // zig-zag: 先自己
    }
    rot(x);
}
if (!goal) root_ = x;
```

注意 `splay(x, goal)` 这个签名同时承担了两件事：`goal = 0` 是"提根"（集合用法），
`goal = a` 是"成为 a 的孩子"（区间提取用法）。**一个函数，两种语义**，这是 Splay 实现短的根源。

`is_right(x)` 写成 `t[t[x].fa].r == x` 是刻意的：NIL 的 `r` 为 0，而节点下标从 1 开始，
所以 `fa == 0` 时它天然返回 `false`，不需要额外判空。

### B. 为什么必须是双旋：路径折半

zig-zig 一次把 `x` 提升**两层**，同时把路径上的一对父子"折叠"成平行关系。
效果是：**完成一次 splay 后，访问路径上每个节点的深度至少减半**。

本期 G5 用一个纯链做了精确验证（顺序插入 1..M 得到的是一条链）：

| M | 插入后树高（双旋/单旋） | 访问一次最小值后（双旋/单旋） |
|---|---|---|
| 400 | 400 / 400 | **202** / 400 |
| 800 | 800 / 800 | **402** / 800 |
| 1600 | 1600 / 1600 | **802** / 1600 |

双旋后的树高精确等于 `M/2 + 2`——链被对折了一次。单旋只把最小值挪到根，
其余 1999 个节点**一层都没少**：`rot` 是"搬运"，不是"压缩"。

代价对比（顺序访问 1..M 共 M 次 `access`）：

| M | 双旋旋转次数 | 单旋旋转次数 | 比值 |
|---|---|---|---|
| 400 | 1 732（4.33/M） | 80 199（0.50/M²） | 46× |
| 800 | 3 490（4.36/M） | 320 399（0.50/M²） | 92× |
| 1600 | 7 024（4.39/M） | 1 280 799（0.50/M²） | 182× |

双旋是**线性**的（顺序访问定理：按序访问 1..n 的总代价 O(n)），单旋是 **n²/2** 的。
比值随 n 线性增长——这就是"均摊界崩塌"的实测形态，不是理论恐吓。

### C. 均摊分析（势能法，结论级）

令 `sz(x)` 为子树大小，`r(x) = log₂ sz(x)`，势能 `Φ = Σ_x r(x)`。有 **access lemma**：

```
splay(x) 的摊还代价 ≤ 3·(r(root) − r(x)) + 1 ≤ 3·log₂ n + 1
```

于是 m 次操作总代价 `O((n + m) log n)`。要点有两条，都容易被忽略：

- 势能是**全局**的，所以"某一次 O(n)"并不违反摊还界——它只是提前支取了势能。
- 双旋是引理成立的前提。单旋时 `ΔΦ` 的上界不再是 `3(r(root) − r(x))`，
  上表第 3 行就是这个结论的实测。

### D. 文艺平衡树：区间即子树

树的位置就是下标，中序遍历就是序列。首尾各放一个哨兵：

```
树中位置   1          2 .. n+1        n+2
内容      -INF        a[1..n]         +INF
用户下标              1 .. n
```

于是任意区间 `[l, r]` 都能被"夹"成一个子树：

```cpp
int extract(int l, int r) {
    int a = kth(l);       // 位置 l：元素 l-1 或 -INF 哨兵
    splay(a, 0);          // a 提到根
    int b = kth(r + 2);   // 位置 r+2：元素 r+1 或 +INF 哨兵
    splay(b, a);          // b 成为 a 的右孩子
    return t[b].l;        // 位置 [l+1, r+1] == 元素 [l, r]
}
```

两次 splay 之后，区间必然落在 `b` 的左子树上——**不需要任何边界特判**，这正是哨兵的价值。
代价是接口下标要 +1：用户写 `[1, n]`，树里是 `[2, n+1]`，`kth` 与 `extract` 各差一次偏移。
这是本期最容易被写错的地方（G3 的随机对拍专门覆盖 `l = 1`、`r = n` 与 `l = r`）。

### E. 双 lazy：`rev` 与 `add` 的不对称

```cpp
void applyRev(int x) { swap(t[x].l, t[x].r); t[x].rev ^= 1; }        // sz/sum/mn 全不变
void applyAdd(int x, long long d) {                                   // 三个聚合量都变
    t[x].val += d; t[x].sum += d * t[x].sz; t[x].mn += d; t[x].add += d;
}
```

由此产生一个**不对称**，也是本期最容易写错的一处：

| 操作 | 打标记后是否需要 `pull` 祖先 |
|---|---|
| `rangeRev` | **不需要**（元素集合没变，`sum/mn/sz` 都没变） |
| `rangeAdd` | **必须**（`sum/mn` 变了，`b` 与 `a` 的聚合量已过期） |

如果以后要维护"区间最大值的位置""区间 LIS"这类**依赖顺序**的量，`rev` 也会改变它们，
那时就必须 `pull`——所以判断标准不是"是 rev 还是 add"，而是"这个聚合量是否依赖顺序"。

### F. `pull` 的纪律：`add` 必须为 0

`pull(x)` 的执行体是 `sum = sum(l) + sum(r) + val`。如果 `x` 身上还挂着未下推的 `add = d`，
那么 `x.sum` 里已经含有 `d·sz(x)`，而 `val` 也已经加过 `d`，`pull` 会把这份贡献**算重或抹掉**：

```
pull 前: sum(x) = sum(l) + sum(r) + val(x) + d·(sz(x) − 1)
pull 后: sum(x) = sum(l) + sum(r) + val(x)          ← d 的贡献消失
```

这就是为什么 `splay` 的第一件事是**把 x 到根的整条路径自顶向下 push 一遍**：

```cpp
path_.clear();
for (int y = x; y; y = t[y].fa) path_.push_back(y);
for (int i = (int)path_.size() - 1; i >= 0; --i) push(path_[i]);
```

push 完之后路径上所有节点的 `add` 都是 0，旋转中的 `pull(y)` / `pull(x)` 才安全。
`kth` 下行时的 `push(x)` 是同一纪律的另一半——不下推就取 `sz(left)`，拿到的是翻转前的值。

本期镜像在 `pull` 里放了一条 `assert(t[x].add == 0)`，故障注入证明它确实能抓住"忘记 push"。

## 三、复杂度对比

| 操作 | Splay | FHQ-Treap | `std::set` | 说明 |
|---|---|---|---|---|
| `insert` / `erase` | 摊还 O(log n) | 期望 O(log n) | O(log n) | Splay 有一次 splay 常数 |
| `rank` / `kth` | 摊还 O(log n) | O(log n) | 不支持 | |
| 单次最坏 | **O(n)** | O(n) | O(log n) | 均摊界不管单次 |
| 按位置插删 | 摊还 O(log n) | O(log n) | — | 隐式键 |
| 区间翻转 | 摊还 O(log n) | O(log n) | — | 都是 O(1) 打标记 |
| 区间加 + 区间最值 | 摊还 O(log n) | O(log n) | — | 双 lazy |
| 建树 | **O(n)**（取中点递归） | O(n log n) | O(n log n) | 本期 `build` |
| 可持久化 | **不适配** | O(log n) | — | 见第五节第 9 条 |
| 每节点空间 | 5×4B = 20B | 20B | ~32B + 分配器头 | 数组池 |
| 自适应 | **有** | 无 | 无 | 提根 |

关于绝对耗时：Splay 的纯查找负载通常比 `std::set` 慢 1.5–3 倍（每次 insert 都要一路旋到根），
这是"自适应 + 区间能力"的代价。**本期未在本机编译，具体数值以实跑为准**；上表只给量级与方向。
基准代码已按阶段分列（insert / query / erase 与 build / sum / add / rev / min），
两个 splay 变体共享同一查询序列（下标由 `i` 的确定性哈希给出），校验和可直接互相比对。

## 四、代码要点

1. **`NIL = 0`，`fa = 0` 表示"无父"**。于是 `is_right(x)` 无需判空，`if (z)` 一句就区分了"z 是根"与"z 有父"。
2. **`splay(x, goal)` 必须先 push 路径再旋转**。本期实测这层 push 在所有调用点都被 `kth` 的 push 覆盖了
   （见故障注入），但它仍是正确做法——一旦换个入口（例如外部持有节点下标），它就变成唯一保障。
3. **插入后不必显式 `pull` 父节点**：`splay` 的第一次 `rot` 会 `pull(y)`，而 `y` 正是新节点的父。
   手动多写一次 `pull` 不会错，但会让人误以为它是必要条件。
4. **删除的两个分支**：无左子树直接让右子树接班；有左子树则把"左子树最大"旋到根再挂右子树。
   关键是 `t[L].fa = 0` 这一句——不写，`splay(m, 0)` 会顺着旧父指针一路旋到已删除的节点上去。
5. **哨兵用节点下标记住，不能用位置或下标值判断**。本期真实 bug，见第五节第 1 条。
6. **`build` 用取中点递归**：O(n) 得到平衡树，省掉 n 次插入与全部旋转。递归深度 O(log n)，安全。
7. **`height()` / `check()` / `to_vector()` 一律迭代实现**：Splay 的瞬时高度可达 O(n)，
   递归版在"顺序插入 2000 个"时就爆栈了（G5 正是这种输入）。
8. **`spins_` 计数器**：只加不减，用于把"旋转次数"这个抽象代价变成可断言的实数。
   G5 的三条断言全靠它。
9. **区间接口统一 1-based 闭区间**，`insertAt/eraseAt/at` 也用 1-based。
   内部再叠一层哨兵偏移（+1），只出现在 `kth` 与 `extract` 两处，别的地方不许出现 `+1`。
10. **`pull` 前确认 `add == 0`**；`applyAdd` 里 `d * sz` 必须用 64 位——`d` 累积到 1e9、`sz` 到 1e6
    就是 1e15，`int` 早已溢出。这是区间加最经典的静默错误。

## 五、常见坑（含本期实测）

1. **哨兵靠"下标"判断（本期真实 bug）**：`toVector` 初版写的是
   `if (x != 1 && x != n + 2) out.push_back(...)`，把"节点下标"当成了"中序位置"。
   实际上 `buildRec` 先创建根节点，所以 1 号节点是**根（一个真实元素）**，哨兵的下标是别的数。
   症状：输出序列开头多一个 `-1000000000000000`（即 `-INFV`），中间少一个真实元素，长度恰好对得上——
   G3 报的是"末态 167 vs 167，first diff @28"，最难查的那一类。
   **修法**：建树时把两个哨兵的节点下标记进 `neg_` / `pos_`。

2. **把均摊结构当成"随时平衡"（本期错误假设）**：初版 G5 断言"顺序插入 1..M 后双旋树高 ≈ log M"。
   实测直接打脸——**两版都是纯链，树高 = M**。原因是每次新键都插在当前根的右孩子位置，
   一次 zig 就上了根，链根本不会被折叠。Splay 的平衡只在**访问之后**才出现，
   而且第一次访问的代价就是 O(n)。这条错误假设是被镜像跑出来的，不是想出来的。

3. **`pull` 覆盖 `add`**：`pull` 重算 `sum = sum(l)+sum(r)+val`，把 `applyAdd` 加进去的 `d·sz` 抹掉。
   镜像的 `assert` 在故障注入中一次就抓到了（`kth` 不 push 的变体）。
   判别口诀：**要么先 push 再 pull，要么别 pull**。

4. **`rangeRev` 忘了 `pull`** 与 **`rangeAdd` 忘了 `pull`**——前者其实不需要，后者必须。
   两种错误方向相反，但都会让"区间和"从某次操作开始随机偏一个常数。

5. **`t[L].fa = 0` 漏写**：删除时把左子树最大值旋到根，若不断开 `L` 与已删节点的父指针，
   `splay` 的目标就不再是 0，循环条件 `t[x].fa != goal` 永远不会满足，**死循环**（不是崩溃，更难发现）。

6. **`kth` 忘了 push**：读到的 `sz(left)` 是翻转前的值，取到的位置是镜像的。
   对拍表现为"某些区间和正确、某些错"，因为只有跨过 rev 生效边界的查询才出错。

7. **递归爆栈**：`height()` 若写成递归，G5 的 2000 长链就是 2000 层。Splay 树没有任何高度保证，
   凡是对树的形状做遍历的诊断函数都该用显式栈。

8. **`add * sz` 溢出**：`int` 版区间加在 `n = 1e6`、累积 `add = 1e9` 时溢出。
   本期用 `long long`，并在 `check()` 里对 `sum` 做了自洽校验——但校验式本身也含 `add*(sz-1)`，
   所以溢出会同时污染数据和校验，只能靠类型选对来防。

9. **可持久化 + Splay = 陷阱**：Splay 的摊还界依赖"整棵树的历史"，路径复制产生的旧版本
   一旦被访问，会把新版本的势能结构打乱，摊还分析直接失效（不是"慢一点"，是"界不成立"）。
   要可持久化就用 0008 的 FHQ-Treap 或 0012 的可持久化线段树。

10. **`extract` 对空区间返回 0**：`rangeRev` / `rangeAdd` 的入口必须先 `l <= r`，
    否则会拿 0 号 NIL 去 `applyAdd`（被 `if (!x) return` 吞掉，静默无操作），
    表现为"空区间操作不报错但也没生效"。

## 六、配套练习

1. **基础**：把 `SplayTree` 改成 multiset（节点加 `cnt` 字段），实现 `count(x)` 与 `eraseOne(x)`。
   注意 `erase` 里的"左子树最大值"逻辑要改成"把 cnt 减一后仍保留节点"。
2. **基础**：用 Splay 实现 LRU 缓存（`get` 命中即 `access` 提根，`put` 溢出时删最左叶）。
   体会"自适应"到底省了什么：正常负载下命中率高的键会稳定停在根附近。
3. **进阶**：给 `SplaySeq` 加"区间赋值"（`assign`）与"区间加"共存的三标记结构，
   写出 `push` 的正确顺序（`assign` 会清空 `add`），并说明为什么 `rev` 可以放在最后。
4. **进阶**：把 `SplaySeq` 的 `mn` 换成"最小值第一次出现的位置"，讨论 `rev` 是否还需要 `pull`。
5. **挑战**：洛谷 P3391【模板】文艺平衡树：1..n 排列，m 次区间翻转，输出最终序列。
   用本期 `SplaySeq` 直接替换主函数，注意 m 次翻转后只做一次中序输出。
6. **挑战**：洛谷 P2596 [ZJOI2006] 书架：五种操作（置顶/置底/前移/后移/查询排名）。
   提示：全部可以归约成"按位置删除 + 按位置插入"，这正是隐式键的强项。
7. **思考题**：为什么 `splay(x, goal)` 里 `goal != 0` 时不需要更新 `root_`？
   如果 `goal` 恰好是 `x` 的后代（非法调用），会发生什么？请给出一个能让程序死循环的构造。
8. **思考题**：本期的 `splay` 在所有调用点都从 `kth` 拿目标，于是"路径 push"是冗余的。
   请设计一个**必须**依赖这层 push 的调用场景，并说明为什么 `kth` 的 push 覆盖不到它。
