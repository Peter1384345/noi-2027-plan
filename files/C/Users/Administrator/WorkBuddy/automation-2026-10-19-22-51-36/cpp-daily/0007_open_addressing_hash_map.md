## 一、为什么高效

`std::unordered_map` 是**节点式链地址法**：每个键值对独立堆分配、桶数组存指针。
一次查找的代价 = 哈希 + 取桶 + **追逐指针**，而指针追逐是现代 CPU 的头号杀手：

| 开销来源 | unordered_map（链地址） | 开放寻址 flat hash |
|---|---|---|
| 内存布局 | 节点散落堆上，每步缓存 miss | keys/vals/state 三个连续数组，顺序探测即顺序预取 |
| 每元素空间 | 节点指针 + next 指针 + 桶指针 ≈ 3×8B 额外 | 仅 state 1 字节（或 Robin Hood 的 psl 4 字节） |
| 插入 | 每次 new（分配器锁/慢路径） | 数组下标写，零分配（除 rehash） |
| 典型速度 | 1× | **3–10×**（插入差距最大，查找 2–4×） |

代价是必须处理两个开放寻址固有问题：**聚簇**和**删除**。本期三个实现给出三种答案。

## 二、原理

### A. 线性探测 + 墓碑（工程首选）

- 插入/查找：从 `h = hash(k) & (cap-1)` 起逐格 `+1`，遇空槽即断（键必不在），跳过墓碑继续。
- 删除不能直接置空——会截断后方同哈希元素的探测链。置为**墓碑**（tombstone）：查找跳过、插入可复用。
- **两个 rehash 触发条件**（缺一不可）：
  1. `(used + tombs) 达负载上限` → 容量翻倍；
  2. `tombs > used` → **同容量** rehash 清墓碑，否则查找链被墓碑无限拉长。

### B. 三角数二次探测（缓解聚簇）

纯 `i²` 探测在容量为 2ᵏ 时只能触达**一半**槽位（i² mod 2ᵏ 的像集只有一半）。
改用三角数 `T_t = t(t+1)/2`：

- **数学性质**：{T_t mod 2ᵏ | t = 0..2ᵏ-1} 恰好取遍全部 2ᵏ 个余数（本期对拍含覆盖性断言：cap=1024 全覆盖）。
- 相邻位移差递增（1,2,3,...），探测路径发散，一次聚簇（primary clustering）明显缓解。

### C. Robin Hood hashing（最优探测分布）

每个元素记录 **PSL**（Probe Sequence Length，距 home 槽的位移）：

- **插入·劫富济贫**：携带者 `cp` > 占位者 `psl` 则交换，被挤者继续下移。效果：所有 PSL 趋于均匀，**方差急剧缩小** → 最坏查找时间从"灾难聚簇"降为 O(log n) 量级。
- **查找·早退**：途中遇到 `psl < 当前距离` 的槽，键必不在——平均未命中查找快于线性探测。
- **删除·后移（backward shift）**：删除产生空洞后，把右邻 PSL>0 的元素逐个前移一格（PSL-1），直到空槽或 PSL=0。表中**永远无墓碑**，早退性质永久成立。
- 因为探测分布均匀，负载可放宽到 **0.85**（线性探测在 0.7 以上已开始劣化）。

### D. 哈希函数：splitmix64

开放寻址的正确性完全依赖哈希的低位随机性。顺序键直接 `k & mask` 会造成灾难性连续聚簇（本期 G4 组专门检验此场景）。splitmix64 三次乘法混合 + 异或右移，雪崩性好、每键约 5ns。

## 三、复杂度对比

| 操作 | LinearMap | TriMap | RobinHoodMap | unordered_map |
|---|---|---|---|---|
| 期望插入 | O(1)/(1-α)² | O(1)/(1-α)² | O(1)/(1-α) | O(1) 摊还 |
| 期望查找命中 | O(1)/(1-α) | 类似 | O(1)（PSL 紧界） | O(1+λ) |
| 期望查找未命中 | O(1)/(1-α)（受墓碑拖累） | 类似 | **O(1)，早退** | O(1+λ) |
| 删除 | O(1) + 可能触发扬内 rehash | 同左 | O(链长) 后移 | O(1) |
| 最坏（单键） | O(n) 全表扫 | O(n) | O(n)（概率极低） | O(n) 单桶 |
| 负载上限 | 0.7 | 0.7 | **0.85** | λ≈1 |
| 额外空间/元素 | 1B state | 1B state | 4B psl | ~24B 指针/节点 |
| 缓存友好度 | ★★★★★ | ★★★★ | ★★★★★ | ★ |

α = 负载因子。实测参考（x86, -O2, N=2e6，量级）：插入 linear ≈ 0.05s / robin ≈ 0.07s / unordered_map ≈ 0.35–0.5s；查找 open addressing ≈ 0.03–0.05s / unordered_map ≈ 0.15–0.25s。以本机实跑输出为准。

## 四、代码要点

1. **负载检查必须用整数比例式** `(used+1) * 100 >= cap * 85`，避免浮点比较；且**必须放在探测之前**——Robin Hood 的交换链要靠"必然存在空槽"终止。
2. **插入复用墓碑**：探测时记下第一个墓碑位置，确认键不存在后放回墓碑处（tombs--），不急着扩容。
3. **容量恒为 2 的幂**：`& mask` 代替 `% cap`；也是三角数覆盖全表的前提。
4. **Robin Hood 插入的三分支顺序**：空槽 → 落位；键相等 → 更新；`cp > psl` → 交换。任何一处顺序颠倒都会破坏不变式。
5. **后移删除的停止条件**：`psl == 0`（元素就在自家 home 槽，无法再前移）或空槽。
6. rehash 时**重建所有元素**（墓碑全部消失、PSL 重新计算），不要试图原地搬运。

## 五、常见坑（本期实测踩过）

1. **负载阈值单位写错 = 死循环**：初版误写 `(used+1)*10 >= cap*85`（语义是负载 ≥ 8.5），扩容永不触发，表满后插入 `while(true)` 永远找不到空槽。镜像对拍以 `INSERT STUCK used=32 cap=32` 精确暴露。教训：阈值比较写整数比例式后，**用代数量纲复核一遍**（×10/100 配 7/70 还是 85）。
2. **查找遇到墓碑必须继续，不能停**：停了就会漏掉后方元素；但墓碑堆积会拖慢查找 → 必须有"tombs > used 同容量 rehash"这条止血规则。
3. **三角数覆盖性依赖容量为 2 的幂**：任意容量下三角数 mod cap 不保证取遍全部余数，会退化成死循环。若要支持任意容量，需另证或改用其它探测序列。
4. **对拍框架自身的 oracle 复用 bug**：多个被测实现若共用同一个 oracle 顺序跑多遍，第一遍的 mutate 会污染后续所有遍的期望值。每个实现必须独立重建 oracle。
5. **顺序键 + 直接取低位**：`k & mask` 对连续整数键产生完美连续聚簇，插入退化为 O(n)。哈希函数是开放寻址的生命线，不是可省略的装饰。

## 六、配套练习

1. **基础**：给 LinearMap 增加 `reserve(n)`——一次性预分配到 `next_pow2(n / 0.7)`，rehash 期间不扩容（对应基准中"rehash 抖动"的消除）。
2. **模板化**：把三个实现改成 `template <class K, class V, class Hash>`，支持任意类型键（提示：空槽/墓碑哨兵对任意 K 不再可行，需要 state 数组——本期已有）。
3. **进阶**：实现 **Robin Hood + 缩容**（used < cap/4 时容量减半 rehash），并验证 max_psl 在缩容前后不劣化。
4. **挑战**：实现 `SwissTable` 风格的**元数据字节**（每槽 1 字节：空/满/墓碑 + 高 7 位哈希指纹），未命中查找可一次 SIMD 比较 16 槽，跳过全部 key 比较——这是 abseil flat_hash_map 的核心。
5. **思考题**：为什么 Robin Hood 的查找早退条件是 `psl < 当前距离`（严格小于）而不是 `<=`？构造一个反例说明 `<=` 会漏查。
